# UAC switches 0c to ENG

User evidence: UAC appearance switches the taskbar indicator to ENG; returning requires Win+Space to reselect 0c. Microsoft Zhuyin does not exhibit this in the same user's comparison. The 0c settings process remains open. Engine survival is not yet independently observed.

This is an input-method selection/restoration problem until evidence establishes otherwise, rather than an ordinary 0c Chinese/English mode toggle. Windows per-application input-method selection and 0c mode-memory are separate settings. No mode-memory change is justified by the current evidence.

Baseline code checks (before the candidate fix):
- The Windows preview uses the unmodified official 0.2.10 native TSF shell; git diff v0.2.10..56a5881 -- platforms/windows is empty. Composition features change the Go engine/settings, not native UAC handling. This narrows the search; it does not rule out every indirect engine interaction.
- register.rs registers six TSF categories and does not include GUID_TFCAT_TIPCAP_SECUREMODE. Microsoft SampleIME includes it: https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/IME/cpp/SampleIME/Register.cpp . The sample is not evidence of Microsoft Zhuyin's exact implementation. Missing secure-mode support is a candidate cause of fallback, not a demonstrated explanation of persistent selection loss.
- ActivateEx records TF_TMAE_SECUREMODE; allowed() blocks forwarding input in that mode. Activate() still warms the candidate helper and probes an existing engine. Adding SECUREMODE alone would advertise behavior this external-engine architecture has not validated on the secure desktop.
- The keyboard open/close notification only toggles internal mode for an observed Ctrl+Space hotkey. It does not choose the Windows ENG keyboard profile.
- Upstream v0.2.11 changes Windows full-width handling; no UAC/profile-restoration fix was identified in its diff/history.

Native Windows follow-up: run platforms/windows/test/uac-profile-probe.ps1 as the ordinary desktop user, focus a normal text window with 0c selected, trigger UAC and cancel, return to the same text window before pressing Win+Space. It samples foreground HKL, desktop availability and 0c process IDs, with no input text, titles, key hooks or setting changes. Compare with Microsoft Zhuyin. HKL does not identify a TIP profile uniquely, so corroborate with the taskbar observation and existing activation logs if needed; do not enable tsf-debug.

Acceptance for a future fix: cancel and accept UAC both preserve selection when returning to the original normal text window; manual switching to ENG still works; native/shared mode-memory remain correct; sensitive/secure input does not reach the normal user engine or learning store. Test same-account elevation separately from different-account administrator credentials. Avoid automatic global profile activation as an unverified workaround.

The read-only PowerShell probe remains source-reviewed only. This Linux environment has no native Windows UAC desktop. The candidate fix below has executable unit-test evidence under Wine, not native UAC acceptance.

Candidate implementation:
- Register GUID_TFCAT_TIPCAP_SECUREMODE using the same list for registration and unregistration. Microsoft's ActivateEx documentation explicitly says only secure-mode-capable text services are activated in that mode: https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfthreadmgrex-activateex . Category definitions: https://learn.microsoft.com/en-us/windows/win32/tsf/predefined-category-values . Weasel also registers this capability: https://github.com/rime/weasel/blob/master/WeaselTSF/Register.cpp . This establishes a real eligibility gap; it does not prove the user's restoration failure is fully resolved.
- Split activation by the actual TSF flags. Secure activation retains only the manager/client identity. It does not subscribe to keys, touch keyboard compartments, construct a candidate callback or language-bar control, warm the UI helper, query/spawn the engine, or write normal activation logs.
- Drop an existing transport without a close message and discard replay/context buffers while keeping remembered native mode. Secure event and menu paths pass through, including late callbacks. Secure deactivation does not inspect focused documents or send hide/close requests.
- Legacy Activate explicitly uses normal flags, so a reused object does not inherit a prior secure activation. Normal editing/composition code and mixed-input decisions are unchanged. No global profile monitor or forced activation was added.

Validation: x64 Windows GNU unit-test executable and production DLL built; i686 Windows GNU tests checked. Four new tests executed under Wine 10: real COM secure activation with a thread manager refusing services, all key-event variants, focus/menu/deactivate paths and zero runtime activity, return to normal activation flags, and session suspension preserving remembered mode without a close request. Ten existing registration/openclose/focus tests also passed. The registration test overlaps the secure and regression runs; there are 14 distinct passing tests. The older Wine 6 could not load the Rust binary because bcryptprimitives.dll is absent, so no results from it are counted.

Native UAC acceptance is still pending. A final Windows package must rebuild/re-register both x64 and x86 TSF shells and perform a clean desktop relogin; the previous engine/settings-only preview helper cannot deliver this native-shell fix. Do not claim successful UAC restoration or distribute the GNU debug DLL as a production installer based on the emulation tests.
