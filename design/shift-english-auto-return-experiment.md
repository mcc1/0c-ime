# 先研究手動英文起點、自動中文終點

狀態：依新的使用情境調整研究順序；目標設計，尚未執行或改產品。此文件優先於[混打意圖 v2](mixed-input-intent-experiment-v2.md)的執行順序。v2 的中文／literal 意圖、不可辨識衝突與資料隔離要求繼續適用，但其 C/A 改善率不能直接套在本實驗。

開跑前目標修訂：使用者指出整段組字與後文證據是核心，因此取消「第二音節截止」及「任何暫時轉字皆算最終誤判」的設定。改評未提交整段的最終結果，以及後文究竟修好多少前面的判斷。此修訂在新實驗、資料與品質結果之前完成；不是依實驗結果放寬門檻。

細化設計見[實驗 protocol v1](shift-return-protocol-v1.md)及[手算計分例](shift-return-worked-scoring.md)。後者是假設輸出演練，不是品質結果。

## 核心目標

使用者在中文輸入時先按 Shift 切到英文，已提供英文片段的起點。**第一階段只判斷何時結束英文片段，並從正確的按鍵邊界恢復中文組字，免去第二次 Shift。** 不同時研究自動開始英文，不重寫全部 mixed-input 邏輯。

例：`[Shift]microsoftsu3cl3`，期望完整保留 `microsoft` 並輸出「你好」。另一個同樣以 Shift 開始的任務可能是帳號 `microsoft593`，它應完整保留；若任務是 `microsoft` 加「窄」，就需要判斷後段中文。Shift 提供起點及英文意圖，並沒有消除終點歧義。

成功是首個中文字也正確組出、英文原文完整保留，不只是模式指示燈切回中文。允許輸入後面的字詞後，自動重新判斷同一未提交組字段的先前切法；使用者打完再手動選字／重打則另計介入成本，不算自動成功。不能要求只看第一音節就永久定案。

例如到 `microsoft593` 時可同時保留帳號與「microsoft窄」；後面出現意圖為「窄小的走道」的注音時，必須檢查成詞及句子證據是否實際提高中文解釋的選擇，並修正先前的 literal 判斷。相反地，帳號後續或刻意用注音按鍵構造的完整帳號，不能只因有中文詞就一律轉字。

## 兩階段分開驗證

| 階段 | 已知條件 | 唯一新增判斷 | 暫不改動 |
| --- | --- | --- | --- |
| S1，優先 | 使用者 Shift 標示英文起點 | 英文何時結束、中文從哪個 raw offset 開始 | 自動進英文、一般中文 decoder、帳號／格式等非目標邏輯 |
| S2，後續 | 起點未知 | 何時進英文；何時回中文 | S1 的終點機制先固定，再測新增起點判斷的影響 |

S1 通過不能宣稱 S2 也通過。S2 比較固定終點機制＋手動起點與同機制＋自動起點，避免把兩種錯誤混在一起。

## 模式語意與來源

現有 `core/proto/proto.go` 的 `Toggle` 表示單按 Shift；`core/session/session.go` 的 `setMode` 處理切換，`key` 在英文且無 composition 時回 `handled=false`，英文字元可能已直接送入應用程式。Shift 目前是持續英文模式，本提案會改變這個語意，必須在明確啟用實驗行為的條件下測試，不靜默更動所有使用者的手動英文選擇。

只將「從中文由 Shift 進英文」當作可自動返回的暫時英文片段。啟動時英文、Caps Lock、外殼指定英文、明確 literal lock 與 private／blocked 等仍依既有行為；不把它們推斷成同一類。再次手動切換、換焦點／欄位、游標移動、貼上與明確選擇等如何終止片段，須在 evaluator 契約固定，不能跨應用程式帶狀態。

如果要等完整中文音節甚至詞才決定，就必須說明在這段等待期間的按鍵由誰持有。**只有 shadow detector，卻把首字按鍵全部直接送進應用程式，並不能完整實現自動回中文。** 離線可先研究辨識能力，但不能把「猜到終點」當作已解決輸出。

輸出實驗必須另固定保留 composition／延後送出的上限與顯示行為，測英文延遲與反悔成本；不能任意刪除已提交到應用程式的文字來補救。保留範圍必須覆蓋要測的整段後文，不能先以兩次聲調等早期窗口凍結答案，再宣稱已測長 context。若成本上限使較長任務提早封存，須如實列失敗／覆蓋限制，不排除該列。這是實作可行性與使用體驗的必要證據，不藉此擴成全域 parser 替換。

## S1 要測的意圖

1. Shift 後輸入英文，再直接打一至多個中文字；包含已知／未知／大寫英文、數字聲母、第一聲空白與明確聲調。
2. Shift 後輸入真正英文、帳號、合成密碼、型號、版本、URL、日期等，整段沒有中文，不能因片段剛好能組字就提早退出英文。
3. 英數識別字完整結束後再接中文；恢復中文時不得侵入識別字，例如把帳號尾碼拿去組首字。
4. 中文起頭含誤按，再接正確中文；分開計首字修正與後續恢復，不把兩件事混算。
5. 相同前綴、後續不同，以及完整觀測相同的相反意圖。逐鍵因果評估：在字詞出現之前不能提前用，但出現之後必須允許重估未提交的前文。完全不可辨識時揭露模式偏好的取捨。
6. 後文強度配對：歧義首音節後分別接能成詞的中文、可支持中文的較長句子、真正 literal 後綴、刻意構造的注音式帳號，以及沒有額外資訊的終止事件。包含單字、短詞及較長組字段，不只測二音節。

每列先記任務意圖、完整英文 span、首個中文 raw offset、可接受讀音／字面與所有 Shift 事件。人工回切的 gold 時刻只能供計分，不能餵給 detector。新 held-out、分組及來源取得遵循 v2；先前已看過的資料只作 development／回歸。

## 對照、指標與目標

對照一為原版手動英文：沒有第二次 Shift 就保持英文，反映需要補按 Shift／重打的成本；對照二為在正確終點人工 Shift 的 reference，確認相同按鍵經正常中文流程能產生預期輸出。後者是參考上限，不是可部署的自動策略。

實驗策略只新增終點判斷。先固定單一 detector 的可見輸入及規則，再評測；如果比較字／詞證據或不同等待長度，每個變因分開命名與對照，不同時換一套學習器、窗口和解碼器。

### 必要的後文對照

在同一局部策略、候選生成、詞庫、參數及原鍵上，比較「只按首個歧義音節的資訊選切法，之後不利用後文重估該切法」與「後文逐鍵到達後，利用詞／句 context 重估同一組未提交解釋」。其他差異不能混入。另以配對決策 probe 固定同一 raw prefix 與 label-free 候選，遮蔽／開放後文評分資訊，確認效果確實來自 context；完整策略則各自記錄因果歷史，不用 gold 過去狀態。

每個 checkpoint 輸出候選切法、完整讀音／字面、詞證據、可用 context、可比較的評分與最終選擇，證明資訊有進入決策，而非只放在 log 或只影響同音字。若模型只能在固定讀音內選同音字，不能冒稱它已用 context 比較「帳號原鍵」與「英文＋中文」兩條解釋。既有 neural API 亦不能直接假定可跨讀音／literal 校準。

報後文修好、後文改壞、仍無法區分的 paired groups；中文切點／讀音改善與同一讀音的選字改善分開。沒有額外資訊的 continuation 是負對照，不應憑增加字數就宣稱更有中文證據。

S1 預定品質目標（所有結果前固定；執行前再補完整事件／分母契約）：

- **正確自動回中文：** 至少90%的 intended-return primary groups，在完整任務輸入完畢、Enter 前，已自動從正確邊界組出首字及完整中文讀音。單音節任務在該音節完成時評分，不排除短詞。Enter 只能提交最後顯示，不臨時另選答案。
- **後文確實有用：** 預先以意圖／按鍵結構標記的「首段有歧義、後文提供區別」隊列，使用後文的完整切點／讀音錯誤須相對不用後文下降至少30%，且 literal 最終錯誤不增加；基準零錯誤則要求維持零，不能宣稱量到改善。另報中文字面選字及修好／改壞數。這個門檻與90%整體成功率都要滿足，不能只挑其中一項。
- **最終英文保留：** literal-only 及 return 任務中的 intended 英文 span，完整任務結束時被錯轉／改寫的 incidence 點估與 Wilson two-sided95上限均≤1%；兩類分開報，不用大量容易的 literal 稀釋誤傷。必要作者保留案例全過。中間可逆的暫時顯示另報 any-event incidence、持續鍵數與反覆次數，不與最終錯誤混算，也不因它曾改變就直接否定後文修正。
- **不吞首字、不破壞英文：** 已判對終點的任務必須完整輸出英文與首個中文字；掉鍵、重複、改寫已提交英文、違反明確鎖定皆0。模式切回但首字仍是亂碼算失敗。
- **使用成本與過程：** 在第一音節、第二音節、每個後續完成音節及整段末尾記正確率；成詞 checkpoints 由 gold 事先標記、僅供計分，不傳給策略。報第二次 Shift 省下的比例、仍需手動介入比例、完整按鍵修正成本、首次判對與最後穩定所需鍵數／音節數，以及英文顯示／送出延遲。機械重播的省鍵數不是已完成使用者體驗驗證；可接受送出延遲、反覆與保留容量的數值須在輸出策略定案後、測試前另固定。

正式隊列至少400個獨立 intended-return groups，以及400個 literal-only groups；英文 span 隊列亦須達400個獨立 groups（可與 return 組共享任務，但需固定 primary span）。其中後文有區別的主對照至少100個獨立 groups，並保留刻意注音式帳號與完全不可辨識組，分開披露。數量不足、無法驗證首字 materialization 或輸出延遲規格未定時，不能給產品整合 GO。未知終點猜測不以原版100%未自動返回作巨大相對改善宣傳，直接報絕對成功率與誤判率。

先驗證偵測是否有足夠辨識能力，再驗證在持有原鍵與完整 composition 的條件下能否正確送出。前者單獨通過只支持繼續做輸出驗證；後者與延遲、保留條件也通過，才支持 S1 功能整合。S2 與安裝包另依各自證據決定。
